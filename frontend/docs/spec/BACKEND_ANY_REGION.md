## 0. Коротко

Сейчас файл участка не из трёх попадает в одну из карточек DS-02 и молча считается бригадами и офисом этой карточки, а точки встают «вокруг» чужого офиса (демо-геокодинг). После §14:

- **Свой участок** хранится в базе: название, офис с координатами, нормативы (тип заявки → навык и минуты), ростер бригад.
- **Дальше всё как у трёх участков кейса:** день, «Построить план», сравнение, события, календарь, запись оператора. Демо-данных у своего участка нет.
- **Разделение работы.** Фронт сам читает любой CSV (кодировка, разделитель, названия колонок), находит точки по адресам и приводит файл к выданному формату Билайна. Бэк хранит участки и применяет к загрузке нормативы, ростер и точки. **Сопоставления колонок на бэке нет.**

Три участка кейса не меняются: ни названия, ни бригады, ни нормативы, ни демо-дни.

## 1. Что присылает фронт

Мастер «Другой участок» в DS-02 (5 шагов: участок и файлы → колонки → нормативы → бригады → точки) по кнопке «Загрузить» делает три запроса подряд:

1. `POST /regions` (новый участок) или `PATCH /regions/{id}` (участок уже есть) — название, офис, нормативы.
2. `PUT /regions/{id}/roster` — ростер участка.
3. `POST /data/import-beeline` — `requests_file`, `control_file?`, `engineers_file`, `region_id`, `date`.

Если шаг 1 создал участок, а шаг 2 или 3 упал — фронт запоминает `region_id` и при повторе шлёт `PATCH`, второй участок не создаёт.

### 1.1. `requests_file` — выданный формат Билайна плюс 4 колонки

UTF-8 без BOM, разделитель `;`, строки `\r\n`, поля с `;` или `"` — в кавычках (RFC 4180). Последняя строка — `Адрес офиса;<адрес>` (адрес без `;`).

```
Заявка;Тип заявки BK;Тип заявки HD;Начало;Окончание;Район;Адрес;Гигабитное подключение;Подключение;Требуемый транспорт;Навык;Длительность;Широта;Долгота
HM-101;Подключение;;08.10.2026 10:00;08.10.2026 12:00;;Химки, ул. Молодёжная, д. 20;Нет;;;installation;70;55.891234;37.443210
HM-110;Авария;;;;;Химки, ул. Спартаковская, д. 7;Нет;;;emergency;80;;
Адрес офиса;Химки, ул. Молодёжная, д. 4
```

| Колонка | Что | Как бэк читает |
|---|---|---|
| Заявка … Требуемый транспорт | как в файлах кейса | как сейчас (`_get`, `_parse_window`, `_required_transport`) |
| `Начало`, `Окончание` | `ДД.ММ.ГГГГ ЧЧ:ММ`; пусто — окна нет | как сейчас: пусто → смена участка |
| **`Навык`** (новая) | `local` \| `installation` \| `emergency` | через `SKILL_ALIASES`; пусто или незнакомое — нет значения |
| **`Длительность`** (новая) | целые минуты работы без дороги, 5–480 | вне диапазона или не число — нет значения |
| **`Широта`, `Долгота`** (новые) | градусы, точка — разделитель | обе есть и в диапазоне — точка из загрузки, геокодер не нужен |

`Навык` и `Длительность` фронт пишет в каждую строку по нормативам участка (шаг «Нормативы»); длительность из исходного файла важнее. `Широта`/`Долгота` — координаты из исходного файла, найденные фронтом по адресу (Photon) или поставленные диспетчером на карте. Не нашли — поля пустые, точку ищет бэк (§5.3).

Новые колонки полезны и для участков кейса: бэк читает их в любой загрузке.

### 1.2. `control_file` — в порядке строк `requests_file`

Фронт сам сопоставляет контрольный файл с заявками (по номеру заявки, а если номера разные, как в файлах кейса, — по порядку строк) и присылает его в том же порядке строк и с обязательными колонками импорта:

```
Заявка;Тип заявки BK;Начало;Окончание;Адрес;Бригада
HM-101;Подключение;08.10.2026 10:00;08.10.2026 12:00;Химки, ул. Молодёжная, д. 20;Смирнов А.
Адрес офиса;Химки, ул. Молодёжная, д. 4
```

Бэк работает с ним как сейчас: `ROWS_MISMATCH` при разной длине, «Бригада» → `dispatcher_engineer_id` по имени бригады в ростере.

### 1.3. `engineers_file` — формат, который бэк уже читает

`_parse_engineers_file`: разделитель `,`, навыки через `;`.

```
id,name,latitude,longitude,shift_start,shift_end,skills,transport,available
E01,Смирнов А.,55.8896,37.4302,09:00,21:00,local;installation,car,true
```

Имена бригад из контрольного файла фронт не меняет, иначе «Реальный диспетчер» не сопоставится. Координаты старта — офис участка.

## 2. Данные: таблица `regions`

Участки кейса остаются в коде (`app/core/regions.py`, `REGIONS`). В базе — только свои участки.

```python
class RegionRecord(Base):
    __tablename__ = "regions"
    id: Mapped[str]              = mapped_column(String(64), primary_key=True)      # "r-3fa2c1d0"
    name: Mapped[str]            = mapped_column(String(60))
    name_key: Mapped[str]        = mapped_column(String(60), unique=True, index=True)  # имя без регистра и лишних пробелов, ё→е
    office_address: Mapped[str]  = mapped_column(String(255))
    office_lat: Mapped[float]    = mapped_column(Float)
    office_lon: Mapped[float]    = mapped_column(Float)
    norms: Mapped[dict]          = mapped_column(JSON, default=dict)   # {"types": [...]}, §3
    roster: Mapped[list]         = mapped_column(JSON, default=list)   # [EngineerIn], §4.5
    request_count: Mapped[int]   = mapped_column(default=0)            # заявок в последней загрузке
    has_control: Mapped[bool]    = mapped_column(default=False)        # был ли контрольный файл
    created_by: Mapped[str|None] = mapped_column(String(64), nullable=True)
    created_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), default=_now)
    updated_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), default=_now)
```

- Миграция не нужна: `init_db` → `create_all` создаёт новую таблицу при старте. На Postgres проверь, что `create_all` запускается при деплое.
- `id` выдаёт бэк: `"r-" + uuid4().hex[:8]`. Фронт принимает любой id вида `[a-z0-9][a-z0-9_-]{0,63}`.
- JSON-поля при изменении помечай `flag_modified(record, "norms")` и `flag_modified(record, "roster")`, как у сценариев.
- Репозиторий: `list_region_records()` (по `created_at`), `get_region_record(id)`, `find_region_by_name(name_key)`, `save_region_record(record)`.

## 3. Реестр участков: `app/core/regions.py`

Один способ получить участок — для кейса и для своего. Форма словаря одна и та же:

```python
{
  "region_id": "r-32a78bea", "name": "Химки",
  "office": {"address": "Химки, ул. Молодёжная, д. 4", "lat": 55.8896, "lon": 37.4302},
  "engineer_count": 3,        # у своего — len(roster)
  "request_count": 20,        # у своего — последняя загрузка
  "dispatcher_assignments": 0, "car_requests": 0,
  "has_control": True, "demo_available": False,
  "builtin": False,           # у участков кейса — True
  "norms": {"types": [...]},  # у участков кейса — BEELINE_NORMS
  "roster": [...],            # только у своего
  "created_at": "2026-10-08T07:58:11+00:00",  # у участков кейса — None
}
```

| Функция | Что делает |
|---|---|
| `BEELINE_NORMS` | `{"types": [Подключение→installation/70, Дозаказ→installation/20, Локальная заявка→local/30, Глобальная проблема→emergency/80]}`: нормативы участков кейса, те же, что `_SKILL_BY_TYPE` / `_DURATION_BY_TYPE` |
| `is_builtin(region_id)` | участок кейса |
| `get_region(region_id, repository=None)` | сначала `REGIONS`, потом база; нет — `None`. Без `repository` открывает свою сессию `SessionLocal` |
| `list_regions(repository=None)` | участки кейса в порядке кейса, затем свои по `created_at` |
| `norm_for(region, type_bk)` | `(skill, minutes)` из `region["norms"]` без учёта регистра и `ё`; нет — `None` |
| `build_region_roster(region)` | участок кейса — `build_region_scenario(id)["engineers"]`; свой — копия `roster` |
| `rule_roster(region, request_count, shift)` | ростер по правилу: `max(3, ceil(n / 5,5))` бригад «Бригада N», у всех `local` и `installation`, `emergency` — у каждой 4-й (0, 4, 8…), автомобиль, смена `shift`, старт — офис |

Участкам кейса при загрузке модуля проставь `builtin=True`, `norms=BEELINE_NORMS`, `created_at=None` — `GET /regions` отдаёт их в той же форме.

## 4. API участков

Формат ошибок — как у импорта: `{"detail": {"error": {"code", "message", "details"}}}`.

**Роли.** `role_allows` проверяет только путь и пускает оператора на `/api/v1/regions` любым методом. Поэтому на `POST`, `PATCH`, `PUT` поставь `Depends(require_roles("dispatcher"))`. `GET /regions` открыт всем ролям. `/regions/{id}/roster` оператору и так закрыт middleware — это правильно.

### 4.1. `GET /regions`

`RegionOut` + 3 поля, старые не меняются:

```python
class RegionOut(BaseModel):
    region_id: str; name: str; office: OfficeOut
    request_count: int; engineer_count: int; demo_available: bool; has_control: bool
    builtin: bool = True
    norms: RegionNorms | None = None
    created_at: str | None = None
```

Порядок: `east`, `south_east`, `south_center`, затем свои по `created_at`. Своим участкам `engineer_count = len(roster)`, `demo_available = false`.

### 4.2. `POST /regions` — создать участок · диспетчер

```json
{
  "name": "Химки",
  "office": { "address": "Химки, ул. Молодёжная, д. 4", "lat": 55.8896, "lon": 37.4302 },
  "norms": { "types": [
    { "type_bk": "Ремонт ТВ", "skill": "local", "duration_minutes": 45 },
    { "type_bk": "Подключение", "skill": "installation", "duration_minutes": 70 }
  ] }
}
```

- `201` + `RegionOut`; `roster = []`, `engineer_count = 0`.
- **Имя:** 1–60 символов, пробелы по краям и двойные внутри убираем. Уникально без учёта регистра и `ё` **среди всех участков, включая участки кейса** → иначе `409 REGION_EXISTS`, `details.region_id` — чей.
- **Офис:** `address` 1–255, `lat` −90…90, `lon` −180…180 → иначе `422`. Координаты обязательны: фронт получает их подсказкой адреса или точкой на карте.
- **Нормативы:** до 200 типов. `type_bk` 1–100 символов, уникален без регистра. `skill` — через `SKILL_ALIASES`, храним ключ: `"Локальные работы"` → `"local"`, незнакомый → `422`. `duration_minutes` 5–480. `norms` можно не передавать — будет `{"types": []}`.

### 4.3. `PATCH /regions/{id}` — изменить свой участок · диспетчер

Тело — любые из `name`, `office`, `norms` (с проверками §4.2); `norms` заменяется целиком. `200` + `RegionOut`. Участок кейса → `409 REGION_BUILTIN` («Участки кейса не меняются»), нет участка → `404 REGION_NOT_FOUND`, имя занято другим → `409 REGION_EXISTS`.

### 4.4. `GET /regions/{id}/roster` · диспетчер

`list[EngineerIn]`. У участка кейса — бригады демо-набора (12/12/11), у своего — сохранённый ростер (может быть пустым). Нет участка → `404`.

### 4.5. `PUT /regions/{id}/roster` — сохранить ростер · диспетчер

Тело — `list[EngineerIn]` (как `engineers_file`, те же валидаторы навыков, транспорта и смены), заменяет ростер целиком. Проверки: от 1 до `settings.max_engineers` бригад, уникальные `id` → иначе `422`. Участок кейса → `409 REGION_BUILTIN`, нет участка → `404`. `200` + сохранённый список.

## 5. Импорт `POST /data/import-beeline`

Параметры не меняются. `import_beeline(...)` получает ещё `region: dict | None`: участок, найденный в маршруте через `get_region(region_id, repository)`.

### 5.1. Участок

- `region_id` передан и есть в реестре — берём его. Передан, но нет → `422 REGION_UNKNOWN` («Нет участка {id}»). Не передан — как сейчас, по строке офиса: определяются только участки кейса.
- **Свой участок:** офис (адрес и координаты) — из участка, строка «Адрес офиса» файла игнорируется. У участка кейса — как сейчас: адрес из файла, координаты из кода.

### 5.2. Навык и длительность по строке

```
навык        = колонка «Навык»        → норматив участка по type_bk → local
длительность = колонка «Длительность» → норматив участка по type_bk → 30
```

- «Норматив участка»: у своего — `norm_for(region, type_bk)`, у участка кейса — `_SKILL_BY_TYPE` / `_DURATION_BY_TYPE`, как сейчас.
- Нет ни колонок, ни норматива → `local` / 30 и тип в `unknown_types` отчёта.
- Срочность, флаг `urgent` и `priority_rank` — как в §13.1 `BACKEND_FIXES_FINAL`: авария по HD «Авария», без HD — по навыку. Правило транспорта (HD «Работа с кабелем», «Авария», гигабит → автомобиль; колонка «Требуемый транспорт» важнее) — без изменений и для своих участков.

### 5.3. Точка заявки

```
колонки «Широта»+«Долгота» → геокодер бэка (если настроен) → [только участки кейса: демо-геокодинг] → офис + geocode_fallback
```

- **Своему участку демо-геокодинг не применяй:** точки «по хешу вокруг офиса» выдуманы, план по ним неверный. Лучше честно «у офиса» и адрес в `geocode_fallback` — фронт покажет замечание.
- Точки из колонок считаются в `coords_from_file`. В `geocoded` — только найденные геокодером бэка.

### 5.4. Ростер дня

| Есть в загрузке | Ростер | `engineers_source` |
|---|---|---|
| `engineers_file` | из файла; у своего участка старт по умолчанию `55.75, 37.62` заменяем на офис | `file` |
| `control_file` | имена из «Бригады»; бригада с тем же именем в ростере участка — как есть, иначе шаблон ростера по кругу с **новым уникальным id** | `control` |
| ничего, у участка есть ростер | ростер участка (у кейса — демо-бригады, как сейчас) | `region` |
| ничего, у своего участка ростер пуст | `rule_roster(region, строк, (SHIFT_START, SHIFT_END))` | `rule` |

Шаблон для «Бригады» — ростер участка, а если он пуст — `rule_roster`. Сейчас у шаблонов повторяются id, если бригад в контрольном файле больше, чем в ростере: выдавай свободные `E01`, `E02`…

### 5.5. Отчёт — новые поля `import_report`

```json
{
  "region_id": "r-32a78bea",
  "region_name": "Химки",
  "coords_from_file": 18,
  "unknown_types": [{ "type_bk": "Непонятное", "count": 1 }],
  "engineers_source": "file",
  "...": "остальные поля — как сейчас"
}
```

Фронт читает их безопасно: нет поля — нет строки отчёта.

### 5.6. После сохранения

У своего участка обнови `request_count` (заявок в дне) и `has_control` (был ли `control_file`). `_guard_day_conflict` (записи оператора → `409 DATE_HAS_BOOKINGS`, прежний CSV-день → архив) — без изменений.

## 7. Запись оператора на свой участок

- Список участков оператор берёт из `GET /regions`: свои участки видны всем операторам.
- Типы заявки для своего участка — из `norms` участка без аварийных (аварии — вкладкой «Авария», событием `urgent_order_added` с `params.region_id`). HD у таких типов нет, фронт шлёт `type_hd` пустым: `/booking/slots` и `/booking/requests` должны принимать его пустым.
- Окна — те же `WINDOWS` 10–22 (§8).

## 8. Не входит в §14

- **Учётки инженеров своего участка.** Бригады без входа в E-экраны. События инженера за них отмечает диспетчер: «Инженер недоступен» и т. п. Если нужно — отдельная задача: логины `eng-<region>-NN`, пароль только из `.env`, в ответах API паролей нет.
- **Удаление участка.** DELETE-ручек не делаем. При необходимости — `PATCH {archived: true}` отдельной задачей.
- **Своя сетка окон записи и своя смена участка.** Запись — по общим окнам 10–22. Смена бригад — из ростера.
- **Дороги за пределами Москвы.** Если `OSRM_LOCAL_ENABLED` и в выгрузке OSRM только Москва — проверь, что для точек области матрица падает на `haversine × road_factor`, а не в 500. На эталоне OSRM выключен, Химки посчитались.

## 11. Выкладка и фронт

- **Поле `builtin` в `GET /regions` — выключатель для фронта.** Появилось — диспетчер видит «Другой участок», свои участки попадают в списки у диспетчера и оператора. Поэтому выкладывайте `builtin` только вместе с ручками §4 и импортом §5, не раньше.
- После выкладки: сверить Swagger (`POST/PATCH /regions`, `/regions/{id}/roster`, поля `RegionOut`), `npm run gen:types`, прогнать §10.3 на стенде на завтрашнюю дату. Восток не трогать.
