## 1. Часы дня (D-24) · P0
**Проблема.** Смена идёт 10:00–22:00. Видео пишем вечером, эксперты откроют стенд после 23:00. При реальном времени:
- событие в 23:00 некуда встроить;
- любое нажатие инженера сразу «Просрочено»;
- после полуночи инженер видит другой день.

«Построить план» работает всегда (`now = shift_start`), а шаги 5–6 демо и экран инженера — нет.

**Решение:** у каждого дня (сценария) свои часы. `clock = null` — реальное время Europe/Moscow, как сейчас.

| Что | Как |
|---|---|
| Хранение | `scenario.clock` (`HH:MM` или `null`). Поле уже есть в `ScenarioOut` |
| ✚ `GET /data/scenarios/{id}/clock` | → `{scenario_id, clock, real_now}` |
| ✚ `POST /data/scenarios/{id}/clock` | тело `{time: "HH:MM" \| null, autoplay: true}` → `{scenario_id, clock, autoplayed: {done: N, in_progress: N, en_route: N}}`. `time: null` — вернуть реальное время |
| Время назад | `time` меньше текущего `clock` → 409 `CLOCK_BACKWARD` «Часы назад не переводятся». Сброс — повторная загрузка дня |
| Где действует «сейчас» | Везде внутри этого дня: `event_time` по умолчанию в `/events/apply`, `at` по умолчанию в `/engineers/*/actions`, SHIFT и флаги `at_risk` / `late` / `reaction_late`, `release_time` срочной заявки |
| ✎ `GET /days/{date}` | в каждом `regions[]` добавить `clock` |
| ✎ `GET /engineers/me/day` | добавить `clock`. «Сегодня» для инженера — день его региона с заданным `clock` и опубликованным планом (если таких несколько — самый поздний по дате); иначе реальная дата |
| ✎ `POST /data/import-beeline`, `/data/load-demo` | `clock` не ставим (`null`): диспетчер ставит сам |

**Автопрогон** (`autoplay: true`, по умолчанию) — при переводе часов вперёд на `T` по всем визитам **применённого** плана дня:

| Условие по плану | Становится | Факт |
|---|---|---|
| `end ≤ T` | `done` | `actual_arrival / start / end` = плановые |
| `start ≤ T < end` | `in_progress` | `actual_arrival` и `actual_start` = плановые |
| `start − travel ≤ T < start` | `en_route` | — |

- У инженеров с такими визитами — `shift_status = on_shift`, `actual_transport = transport`.
- Визиты, по которым инженер уже нажимал сам, не трогаем.
- Флаги пересчитать после прогона.
- Без автопрогона в 12:30 все утренние заявки станут «Просрочена».

**Сид стенда:** при старте (идемпотентно) создать демо-день Востока на сегодняшнюю дату: план построен и опубликован, `clock = 12:30`, автопрогон выполнен. Эксперт в любое время суток попадает в середину рабочего дня.
[Д] Если день уже есть — не пересоздавать. Отдельной кнопки для этого не нужно.

**Приёмка:**
1. `POST clock {time: "12:30"}` на опубликованном дне → визиты до 12:30 «Выполнена», идущие — «В работе» / «В пути», просрочек от прогона нет.
2. `events/apply` без `event_time` → событие в 12:30, авария встаёт в план.
3. `eng-east-01` → `/engineers/me/day` показывает этот день и `clock: "12:30"`; `en_route` без `at` записывается на 12:30.
4. `time: null` → снова реальное время.
5. Время назад → 409.

**Что должно попадать в `GET /events?scenario_id`:**

| Что | `event_type` (названия — на твой выбор, пришли список) | Пример `headline` |
|---|---|---|
| События диспетчера и оператора | как сейчас | «Авария №U-0001 → Бригада Соколов, прибытие 13:25; 2 заявки переданы другим» |
| Применение версии | `plan_applied` | «Версия 4 применена. Инженеры получили обновление» |
| Факты инженера: в пути, в работе, выполнена, прервал | `engineer_action` + `action` | «Бригада Соколов прибыла на аварию №U-0001 · реакция 55 мин» |
| Смена флага «Под угрозой» / «Просрочена» | `at_risk`, `late` | «Бригада Белузин отстаёт на 25 мин: №305867214 под угрозой» · «№305866410 не начнётся в окне 14–16. Предложено переназначить на Бригада Комарь» |
| Запись оператора встроена | `order_added` | «Заявка №305874410 встроена к Бригада Перов, окно 16–18» |

**Поля** — в `payload` или в корне `EventItem`:
- `headline` — одна строка для диспетчера;
- `source` — `dispatcher | operator | engineer | system`;
- `event_time` — HH:MM по часам дня (§1);
- `order_id`, `engineer_id` — если есть;
- `status` — статус заявки после события;
- `flag` — если событие про флаг;
- `applied_at` — HH:MM, когда предложение приняли.

**`needs_decision = true`, если:**
- предложение ждёт решения;
- заявка в `cancel_pending` / `reschedule_pending` (тогда `result_plan_id` — её предложение);
- «Просрочена» с предложением переназначить.

Флаги пишем в ленту только **при смене флага**, не на каждый пересчёт (как в D-04).

## 3. Контракт `params` для событий диспетчера + адрес аварии · P0
`ApplyEventRequest.params` в схеме — произвольный объект. Фронт шлёт так. **Если у тебя названо иначе — ответь, фронт подстроится.**

| `type` | Где в интерфейсе | Верхний уровень | `params` |
|---|---|---|---|
| `urgent_order_added` | «Добавить событие» → «Срочная заявка» | `plan_id`, `event_time`, `request` (RequestIn) | — |
| `order_cancelled` | «Добавить событие» → «Отмена», «Отменить заявку» в карточке | `plan_id`, `event_time`, `order_id` | `{reason: "client_refused" \| "other", comment?}` |
| `engineer_unavailable` | «Добавить событие» → «Инженер недоступен»; «В день» → выкл. в «Состав и ресурсы» | `plan_id`, `event_time` (= «с какого времени»), `engineer_id` | `{reason?}` |
| `transport_changed` | «Состав и ресурсы» после публикации | `plan_id`, `event_time`, `engineer_id` | `{transport: "car" \| "walk" \| "bike" \| "public_transport"}` |
| `engineer_available` | «В день» → вкл. в «Состав и ресурсы» | `plan_id`, `event_time`, `engineer_id` | — |

**`request` срочной заявки** фронт заполняет сам:
- `id: "U-…"`;
- `address` — **свободный текст**, как ввёл диспетчер;
- `duration_minutes: 80`;
- `window_start = event_time`, `window_end` — максимальный `shift_end` бригад региона на смене (в CSV-днях 22:00, в синтетике 19:00);
- `priority: "urgent"`, `required_skill: "emergency"`, `required_transport` (по умолчанию `"car"`);
- `type_bk: "Глобальная проблема"`, `type_hd: "Авария"` (с 29.09 только «Авария», §13.1).

**Геокодинг — обязательно.** Если `latitude`/`longitude` нет, геокодь адрес: кэш → геокодер (если есть сеть) → центроид района. Иначе авария встанет без точки на карте и без расчёта дороги.

## 8. Инженер (добавлено 28.09)
Основание: согласованный макет инженера (`design/Engineer.dc.html`, D-30…D-32) и живая схема на 28.09. В схеме у `EngineerActionIn.action` нет `incident`; в `EngineerVisit` нет `actual_start`, `actual_end`, `equipment`; `GET /engineers/me/day` не типизирован.

**8.1. Баннеры · P0.** В `banners[]` каждый элемент — `{type, text, at, request_id?}`. `at` + `type` фронт использует как ключ «уже просмотрено», поэтому у одного баннера они не меняются между опросами. Тексты — готовые, фронт их не собирает:

| Повод | `text` |
|---|---|
| Новая срочная заявка встала в маршрут | «Новая срочная заявка №{id} — после текущей» |
| Заявку передали другому | «Заявка №{id} передана другому инженеру» |
| Изменился порядок | «Порядок изменён: №{id} теперь {N}-я» |
| Диспетчер принял отмену / перенос | «Отмена №{id} подтверждена» / «Перенос №{id} подтверждён» |
| Диспетчер отклонил | «Диспетчер вернул №{id} в план» |
| Принята недоступность | «С {HH:MM} ваши заявки переданы другим» |

Баннер появляется, когда **применена** версия плана, затронувшая этого инженера. Пока предложение ждёт диспетчера, баннера нет.

**8.2. Активная заявка после «Прервать» · P0.** После `fail` заявка в `cancel_pending` / `reschedule_pending` не считается активной: `active_request_id = null`, и `en_route` к следующей заявке проходит без 409 «две активные заявки». По `BACKEND_SPEC` §5.1 «следующая заявка инженеру доступна сразу» — проверь, что так и работает.

**8.3. Причина «Другое» · P0.** `fail` принимает `payload.reason`: `client_refused | no_access | technical | client_reschedule | other`.
- `client_reschedule` — обязательно `desired_date` (YYYY-MM-DD).
- `other` — обязательно `comment`; без него 422 с кодом `COMMENT_REQUIRED`.
- Строку «Нет доступа или техническая причина» фронт шлёт как `no_access`.

**8.4. Действие `incident` · P1** (из бэклога §6):

| `payload.reason` | Что делает бэк |
|---|---|
| `transport_broken` + `new_transport` | событие `transport_changed` → предложение диспетчеру |
| `cannot_continue` | событие `engineer_unavailable` с текущего времени → предложение |
| `other` + `comment` | запись в ленту, `needs_decision = true`, без перерасчёта |

Разрешено у активной заявки и у текущей запланированной. Ответ — как у остальных действий (`EngineerActionOut` с `day`). Добавь `incident` в описание `EngineerActionIn.action`: фронт показывает кнопку, только если видит его в `/openapi.json`.

### 9.1. Авария от оператора · P1
**Почему.** По `BACKEND_CHANGES` §1 оператору закрыт `/days`. Поэтому фронт не знает `plan_id` активного плана и часов дня. Без `plan_id` бэк берёт «последний сохранённый план» — это может быть чужой регион. `RequestIn.window_start/window_end` обязательны, а правильное «сейчас» (часы дня) есть только у бэка.

**Что шлёт фронт:**
```json
POST /api/v1/events/apply
{ "type": "urgent_order_added", "source": "operator", "apply": false,
  "params": { "region_id": "east", "comment": "Нет связи у всего подъезда, клиенты звонят с 12:10" },
  "request": { "id": "U-LZ3K9Q", "address": "Волгоградский пр-т, д. 128 к1 (ТКД)", "duration_minutes": 80,
               "window_start": "00:55", "window_end": "22:00",
               "priority": "urgent", "required_skill": "emergency", "required_transport": "car",
               "type_bk": "Глобальная проблема", "type_hd": "Авария", "source": "operator" } }
```
`plan_id` и `event_time` не шлём. `window_*` — заглушка: реальное время браузера и 22:00.

**Что сделать, если `source = "operator"`:**
1. План — активный (`applied`) план региона `params.region_id` на сегодня.
2. Время события — часы дня (`scenario.clock ?? сейчас`). Окно аварии: `window_start` = это время, `window_end` = максимальный `shift_end` бригад региона. Присланное `request.window_*` игнорировать.
3. `params.comment` — в строку ленты и в предложение диспетчеру, например: «Авария №U-LZ3K9Q от оператора: «Нет связи у всего подъезда…»».
4. Геокодинг адреса — как для аварии диспетчера (`BACKEND_FIXES_27-09` §3).
5. Ответ — как сейчас: `ReplanResult` со `status: "proposed"`. Диспетчер видит баннер и строку «требует решения».

**Ошибки:**
- нет активного плана на сегодня → 409, `message`: «Рабочий день в регионе {Восток} ещё не начат — аварию примет диспетчер»;
- `params.region_id` не из `region_ids` оператора → 403.

**Приёмка:** под `operator` запрос выше при часах дня 12:30 → предложение в нужном регионе, у заявки `window_start = "12:30"`, в ленте есть комментарий.

### 9.3. Отмена: коды причин и комментарий · P1
**Почему.** В схеме `BookingCancelIn = {reason?: string}`, поля для текста нет. Причины оператора согласованы: «Клиент отказался», «Ошибка записи», «Другое» + обязательный текст — как у диспетчера (`order_cancelled`) и инженера (`fail`).

### 9.4. `message` в ответах · P1
**Почему.** Текст зависит от того, начат ли день. Фронт этого не знает: `/days` оператору закрыт. Нужен готовый текст для тоста.

| Ручка | Случай | `message` |
|---|---|---|
| `POST /booking/requests` | день не начат → полный пересчёт | «Заявка №{id} записана на {DD.MM}, {14–16}. План дня пересчитан» |
| | день начат, встроена | «Заявка №{id} записана на {DD.MM}, {14–16}. План дня пересчитан» |

| `/cancel` | день не начат | «Заявка отменена. План на {DD.MM} пересчитан» |
| | день начат | «Заявка отменена. Чем занять освободившееся окно, решит диспетчер» |
| `/reschedule` | любой | «Заявка №{id} перенесена на {DD.MM}, {14–16}» |

- У `/reschedule` в ответе ещё `request_id` (если при переносе номер меняется), `date`, `window` новой записи.
- Ответ `/cancel` и `/reschedule` можно описать схемой `BookingMutationOut {status, message, request_id?, date?, window?}`, тогда фронт возьмёт тип из OpenAPI.

### 13.2. Не вызывать «из дома» бригаду, которая сегодня не работает · P0
**Ответ №62:** новая заявка или авария сама по себе не должна выдёргивать из дома сотрудника, который по первоначальному плану в этот день не работает. Это допустимо только как эскалация при форс-мажоре.

**Что расходится.** Наш план экономит бригады. Незадействованные бригады числятся в ростере «на смене», поэтому `handle_urgent` и `insert` могут взять их первыми как «свободные». Это против ответа и даёт в предложении «Инженеров N → N+1» — [Г]: проверь на сайте аварией в 12:30.

**Что сделать:**
- **«Работает сегодня»** — у бригады есть хотя бы одна заявка в первой применённой версии плана дня. Или диспетчер включил её явно:
  - `engineer_available`;
  - «Добавить инженера» (§12);
  - ручное переназначение на неё (`/reassign`).
- **`handle_urgent` и все `insert` в начатом дне** берут кандидатов только из работающих сегодня. Это касается вытеснения, отмены, недоступности и записи оператора.
- **Никому из работающих не помещается** → заявка не назначена с причиной, плюс рекомендация `extend` «+1 инженер с навыком …». Это и есть эскалация: решает диспетчер (DS-09 или ручное переназначение).
- **Полный расчёт не меняем:** `/planning/run`, пересчёт будущего дня после записи (D-18). Там выбор бригад и есть планирование.
- **Ручное переназначение на неработающую бригаду разрешено** — это эскалация диспетчера. В ответ `/reassign/check` добавь `engineer_idle_today: true | false`. Фронт покажет метку «Не работает сегодня». Без поля фронт считает её сам: у бригады 0 заявок в текущем плане.

**Приёмка.** Опубликованный план Востока, авария при часах 12:30 → в предложении число инженеров не растёт. Если из работающих с навыком «Аварийные работы» не успевает никто — авария всё равно уходит работающей бригаде с минимальным прибытием (правило «все заняты»).

## Для сведения — решения, которые меняют вызовы фронта

**Диспетчер**
- «Построить план» в CSV-дне = `POST /planning/run` + сразу `POST /planning/{id}/apply`. Черновика у CSV-дня нет (D-25).
- CSV грузится на сегодняшнюю дату без выбора: `date` = сегодня (D-26).
- Фильтров по флагам нет; в `/calendar` фильтры по одному значению, мультизначения не нужны (D-27).
- Часы дня фронт не переводит, только показывает. Для видео ставим их через `POST /data/scenarios/{id}/clock` в Swagger (D-28).

**Инженер**
- `en_route` фронт шлёт только по текущей заявке: `active_request_id`, иначе первая запланированная по `sequence`. Ветку «В пути не по порядку» фронт не использует (D-30).
- `at` в действиях инженера фронт не шлёт — время берёт бэк по часам дня (§1).
- `delay` фронт не использует (D-14).

**Оператор**
- Оператор не вызывает `/days`, `/planning`, `/data`, `/calendar`. В аварии не шлёт `plan_id` и `event_time`.
- Поиск — без `region_id` и `date`, по всем регионам пользователя; от 3 символов, debounce 300 мс.
- Кнопки «Перенести» и «Отменить» — у любой найденной заявки. Статус фронт не проверяет, допустимость решает бэк (9.9, D-34).
- Окна на шаге «Дата и окно» фронт обновляет каждые 30 с: 2 запроса в минуту на открытую вкладку оператора.
- Строку «Навык · N мин на адресе» фронт берёт из `required_skill` и `duration_minutes` ответа `/booking/slots`. Длительности на фронте не зашиты.
- Требуемый транспорт в форме подставляется по правилу `ML_SPEC` §2: «Работа с кабелем» или гигабит → `car`. Оператор может поменять, фронт шлёт итоговое значение.
- `technology` фронт шлёт только для Востока, для остальных регионов — `null`.

**Что фронт закрывает сам — делать ничего не нужно**
- Три формата ошибок → один разборщик на фронте.
- В `ReplanResult` нет diff → фронт вызывает `GET /planning/{new}/diff?against=`.
- В `ExplanationOut` нет разбивки на три ограничения → фронт строит её из `RoutePoint`, `RequestOut` и `EngineerOut`.
- В `RoutePoint` нет полей заявки → фронт грузит `GET /data/scenarios/{id}`.
- В сравнении нет «неназначенных» → фронт берёт их из `PlanResponse.metrics` и `coverage_pct`.
- Порядок координат в `RouteOut.geometry` не описан → фронт берёт линии из `/visualization/{id}/geojson`.
- `order_id` вместо `request_id` в событиях и переназначении → фронт шлёт `order_id`.
- В синтетических наборах нет адреса, района, типа BK/HD, гигабита, имени бригады и реального распределения → фронт подставляет подписи по навыку и id, колонка «Реальный диспетчер» — «нет данных».
- У инженера в визите нет требуемого транспорта и координат → предупреждение в «На чём сегодня?» фронт показывает по несовпадению со справочником, ссылки в Яндекс Карты строит по `/engineers/me/route`.
- **Формы ответов без схемы** фронт снимет со стенда скриптом (`npm run snapshot`):
  - только по явной команде;
  - на **отдельном дне** — `load-demo` на дату через 30 дней;
  - после события делает `reject`.

  Проверь только, что демо-учётки из гайда работают на стенде.
