# Алгоритм распределения заявок

`dispatch/` — алгоритмическое ядро, которое вызывает бэкенд через `backend/app/services/algorithm_adapter.py`. Основной вызов — `dispatch.production.solve_production`: построение допустимых маршрутов, поиск ALNS, рекомбинация пула маршрутов целочисленным решателем HiGHS и независимая проверка плана. Column generation доступен отдельным экспериментальным режимом и не включён по умолчанию.

Планы сравниваются лексикографически: сначала число неназначенных заявок рангов 1, 2 и 3, затем число задействованных инженеров, пробег и мягкий штраф за лишние переходы между зонами. Поиск ограничен временем; глобальный оптимум большой задачи не гарантируется. Жёсткие ограничения включают квалификацию, требуемый транспорт, временное окно, длительность работы и смену. Подробная схема и соответствие коду — в [документации решения](../../docs/SOLUTION.md).

## Воспроизведение метрик

[Проверка на кейсе 2026](benchmark/case_2026/README.md) содержит исходные CSV, явные допущения для недостающих полей, сохранённые результаты, тесты и **одну команду** для полного повторного прогона. Она использует этот же пакет `dispatch`, а не отдельную копию решателя.

Основной результат на 205 исходных заявках в трёх смоделированных сценариях: 604/615 назначений против 334/615 у FIFO, 0 нарушений жёстких ограничений, 20/20 совпадений с точным решением на малых задачах. Сравнение пробега с FIFO не трактуется как экономия при равном объёме выполненных заявок. Оценка контрольного распределения и ML на синтетической истории приведены отдельно с ограничениями их интерпретации.
