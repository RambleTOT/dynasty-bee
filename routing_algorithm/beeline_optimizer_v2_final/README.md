# Рекомендуемый решатель v2 (2026): ALNS + Sequential Lexicographic Column Generation + Integer Master

Для основной версии используйте:

```bash
python -m dispatch hybrid-v2 examples/demo_30.json --seconds 30 --out final_plan.json
```

Архитектура v2: (1) hard feasibility по skill level / tools / transport / shifts / time windows; (2) regret insertion + ALNS быстро строят допустимый incumbent и route pool; (3) restricted integer master рекомбинирует найденные маршруты; (4) **sequential lexicographic LP master** получает dual prices отдельно на стадиях urgent misses -> all misses -> new engineers -> distance; (5) ESPPRC label-setting pricing добавляет отрицательные reduced-cost маршруты; (6) final integer master решает те же цели последовательно. `dispatch/hybrid_v2.py` — pipeline, `dispatch/lexicographic_cg.py` — новый CG.

На 30 малых задачах, где полный route enumeration даёт настоящий глобальный optimum, v2 совпала с ним **30/30** (предыдущий hybrid: 29/30). На 9 case-shaped задачах из структуры данных кейса медиана времени v2 — **2.23 с**; подробности и обязательные оговорки — `reports/v2/BENCHMARK_V2.md`. Это не доказательство глобальной integer-оптимальности больших задач: для такой гарантии потребуется полноценный Branch-and-Price.

Ключевые документы:

- `ALGORITHM_V2.md` — низкоуровневая математика и псевдокод;
- `reports/v2/BENCHMARK_V2.md` — новая валидация и ablation;
- `PUBLIC_DATASETS.md` — внешние реальные датасеты для следующего benchmark;
- `reports/v2/*.json` — сырые результаты прогонов.

# Dispatch Optimizer

Алгоритмическое ядро для распределения заявок и маршрутизации выездных инженеров.
Версия 0.1.0 · подготовлено 17 сентября 2026 года.

**Это работающий исследовательский прототип, не заявление о мировом рекорде.** Внутри: адаптивный поиск маршрутов, целочисленная оптимизация их комбинации, перепланирование, сценарная оптимизация риска, модуль обучения CatBoost и независимые проверки корректности. Интерфейс, геокодирование и подключение к картографическому сервису сюда не входят.

## Что читать

- `RESEARCH_AND_DESIGN.md` — математическая постановка, источники, устройство алгоритма и ограничения.
- `DATASETS.md` — первичные источники данных, корректные цели обучения, условия использования и команды.
- `reports/BENCHMARKS.md` — результаты **реально выполненных** проверок; все исходные задачи и найденные планы сохранены рядом.
- `reports/input_audit.json` — аудит загруженного архива оператора связи.

## Запуск

Python 3.11–3.13. Проверенная среда: Python 3.13.5, NumPy 2.3.5, SciPy 1.17.0, Numba 0.65.1. Для ML дополнительно проверены pandas 2.2.3 и CatBoost 1.2.8. PyArrow в среде выполнения отсутствовал; чтение настоящего TLC Parquet не запускалось.

```bash
python -m venv .venv
source .venv/bin/activate
# Windows: .venv\Scripts\activate
pip install -r requirements.txt

python -m dispatch solve examples/demo_30.json \
  --seconds 30 --iterations 1000 --master-seconds 8 \
  --workforce-bound --out plan.json
```

Первая операция может потратить дополнительное время на JIT-компиляцию Numba. Предел `--seconds` мягкий: текущая операция поиска или решателя может немного выйти за него. Риск, вычисление нижней границы и необязательный внешний генератор маршрутов имеют отдельные бюджеты.

Генерация нового **полностью синтетического** примера:

```bash
python -m dispatch demo --tasks 100 --engineers 12 --seed 42 \
  --pattern tight --seconds 30 --iterations 1000 \
  --save-instance example.json --out plan.json
```

Проверка риска под **необученной синтетической** моделью задержек:

```bash
python -m dispatch solve examples/demo_30.json --seconds 15 \
  --synthetic-risk --risk-seconds 10 --risk-distance-tolerance 0.05 \
  --out risk_plan.json
```

Здесь 96 сценариев используются для выбора плана, ещё 256 независимых — для проверки. Эти вероятности не являются оценками реального риска оператора связи.

Вместо синтетики можно передать собственные сценарии:

```bash
python -m dispatch solve instance.json --risk-npz scenarios.npz \
  --risk-origin LOCAL_CALIBRATION_2026_08 --risk-seconds 10 --out plan.json
```

NPZ содержит `travel` формы `S × K × V × V` и `service` формы `S × K × N`, в минутах. Порядки инженеров, узлов и заявок должны точно совпадать с `instance.json`. Передача NPZ через CLI не создаёт независимую проверочную выборку автоматически: её нужно подать отдельно в `evaluate_risk`.

## Приоритеты оптимизации

Сравнивается кортеж:

```text
(неназначенные срочные, все неназначенные, задействованные инженеры за день, метры)
```

Сначала уменьшается первый компонент, затем второй и т. д. Это выбранная и явно зафиксированная бизнес-политика. Она означает, в частности, что одна дополнительно обслуженная срочная заявка важнее нескольких обычных. Если такая политика заказчику не подходит, её необходимо согласовать и изменить во всех компонентах: `Evaluator.key`, правилах поиска, `master`, `risk`, нижних границах и тестах. Простой смены подписи в интерфейсе недостаточно.

При одинаковом покрытии приоритет численности перед километрами — также решение данной реализации: в PDF перечислены две метрики, но однозначный способ разрешения их конфликтов не задан. Номинальный оптимизатор не подменяет это произвольной суммой штрафов.

Риск-режим — отдельный явный компромисс: сохраняет количества назначенных срочных и всех заявок, не увеличивает число инженеров, но допускает до 5% дополнительных метров относительно найденного номинального плана. Конкретный набор обслуживаемых обычных заявок при неполном покрытии может измениться. Это не тот же самый критерий, что строгий минимум километров.

## Что гарантированно проверяет код

Для возвращённого плана проверяются необходимые навыки и транспорт; начало работы внутри окна заявки; время поездки, ожидания и обслуживания; завершение последней работы до конца смены; отсутствие повторных назначений; индивидуальные стартовые точки; зафиксированные назначения. Маршрут открытый: возврата к старту нет.

**Окно ограничивает начало работы, не окончание.** Работа в 11:50–12:30 допустима для окна 10:00–12:00, если смена продолжается. Задача не может начаться раньше своего `release_time`.

Допустимость проверяется относительно переданных номинальных матриц и длительностей. Это не гарантия отсутствия реальных задержек.

## Программный интерфейс

```python
from dispatch import Instance, SearchConfig, solve
from dispatch.explain import explain_task

instance = Instance.load("instance.json")
result = solve(instance, SearchConfig(
    seed=42, iterations=1000, time_limit_seconds=30, master_seconds=8,
))

# JSON-совместимый результат для backend/UI.
plan = result.report
# Индексы заявок в instance.tasks, по одному кортежу на инженера.
routes = result.routes
# Пул найденных допустимых маршрутов — вход дополнительной оптимизации риска.
pool = result.pool

explanation = explain_task(instance, routes, instance.tasks[0].id)
```

`plan` содержит `objective`, `planned_count`, `active_engineers_today`, `future_distance_km`, маршруты с временами прибытия/начала/окончания, причины неназначения и диагностические данные поиска. `explain_task` дополнительно проверяет локальные переносы выбранной заявки к другим инженерам. Он не выдаёт локальную проверку за доказательство отсутствия лучшего глобального решения.

### Контракт входных данных

Полный пример — `examples/demo_30.json`. Времена можно задавать целыми минутами от общего начала дня или строками `HH:MM`; длительности — целые минуты; расстояния — **целые метры**, не километры. Дробные матрицы отвергаются, а не молча обрезаются.

```python
from dispatch.model import Task, Engineer, Instance
import numpy as np

instance = Instance(
    tasks=[Task("A", node=1, duration=30, window_start=600,
                window_end=720, skill="installation", transport="car")],
    engineers=[Engineer("E1", start_node=0, shift_start=540,
                        shift_end=1080, skills=("installation",), transport="car")],
    travel_minutes={"car": np.array([[0, 20], [23, 0]])},
    distance_m={"car": np.array([[0, 8000], [9200, 0]])},
)
```

Матрицы могут быть асимметричными. Для каждого вида транспорта — отдельная матрица. Поддерживаются произвольные обозначения транспорта и навыков; справочники из кейса должны задаваться согласованно. Входной контракт требует хотя бы одного инженера; полную недоступность задавайте через `available=False`.

Опциональный `service_by_engineer` формы `K × N` позволяет задавать разные времена выполнения одной заявки разными инженерами, например из ML-модели. В этой версии транспортные матрицы фиксированы на один снимок планирования, а не зависят от времени выхода с каждого узла.

### Обработка архива оператора связи

```bash
python scripts/audit_case.py "Билайн Бизнес — исходные материалы.zip" \
  --output reports/input_audit.json
```

В архиве по 66, 83 и 56 действительных заявок для трёх территорий, всего 205 в каждом варианте — синтетическом и контрольном. Пустые строки и строка «Адрес офиса» не являются заявками. Адреса офисов сохраняются отдельно; это возможные стартовые точки, но связь с инженерами нужно подтвердить.

Преобразование `dispatch.case_data.normalize_requests` требует явных справочников `duration_by_type`, `skill_by_type`, геокодированных `request_nodes`, таблицы инженеров и матриц. Неизвестный тип вызывает ошибку. Нельзя использовать ширину окна как длительность работы или объявлять «Глобальную проблему» срочной без согласованного правила. Контрольное назначение бригады не доказывает оптимальность и не является меткой фактической длительности.

## Перепланирование

```python
from dispatch.replan import EngineerState, replan

# updated_instance уже содержит новую заявку и необходимые узлы/матрицы.
# states — реальные сведения для КАЖДОГО инженера, а не вывод из старого расписания.
residual_instance, new_result = replan(
    updated_instance=updated_instance,
    previous_report=old_result.report,
    event_time=13 * 60,
    states=states,
    completed_ids=actually_completed_ids,
    cancelled_ids=set(),
    config=SearchConfig(time_limit_seconds=10, master_seconds=3),
)
```

Для свободного инженера `start_node` — текущая точка, `available_at` — момент готовности. Для инженера, занятого неизменяемой работой, это точка и время **после завершения данного обязательства**, а идентификаторы работ перечислены в `committed_task_ids`. Они исключаются из переменной части маршрута, но не помечаются уже выполненными. `locked_future_prefix` защищает согласованные ближайшие визиты. При несовместимых обязательствах возвращается ошибка, а не молча нарушается обещание клиенту.

Количество задействованных людей учитывает `used_today`, поэтому уже работавший человек не «исчезнет» из дневной метрики после перепланирования. Фактический пройденный путь передаётся в `actually_travelled_m` и суммируется с новым оставшимся маршрутом отдельно от его оптимизируемой длины. Отмена текущей работы требует явной обработки прерывания и оставшейся длительности; здесь она не имитируется.

`changes` показывает переназначения и изменения индексов. Сдвиг позиции после удаления выполненных работ сам по себе не означает реальную перестановку — интерфейс должен сравнить оставшиеся последовательности. Штраф за переназначения доступен в `risk_recombine(stability_weight=...)`; базовый номинальный поиск фиксирует обязательства, но не обещает минимум всех остальных перестановок.

## ML

```bash
pip install -r requirements-ml.txt
python scripts/train_duration.py history.csv \
  --features job_type,district,planned_km,hour,engineer_experience \
  --categorical job_type,district \
  --date-column date --target duration_minutes \
  --origin LOCAL_ACTUAL_SERVICE_LOGS --out service_model
```

Модель использует только перечисленные признаки. Это не автоматический детектор утечек: автор признаков обязан исключить сведения, недоступные на момент планирования. Разбиение — по целым последовательным дням: обучение, калибровка, итоговый тест. Сохраняются две модели `.cbm`, метаданные и метрики на последнем временном блоке.

```python
from dispatch.ml import QuantileDurationModel, service_matrix

model = QuantileDurationModel.load("service_model")
# По одной строке на пару (engineer_id, task_id), с нужными признаками.
instance.service_by_engineer = service_matrix(instance, pair_features, model)
```

Медиана применяется как номинальная длительность; верхняя квантиль может использоваться для более консервативных построений. Сумма верхних квантилей не даёт автоматически такую же вероятность своевременности всего маршрута. В комплекте **нет модели, обученной на фактических результатах оператора связи**, и нет обещания переноса модели такси Нью-Йорка на ремонтные работы.


40 тестов прошли в среде подготовки. Среди них независимый полный перебор трёх малых экземпляров с 5 заявками, проверка всех групп ограничений, работа с фактическими состояниями, защита обязательств, сериализация, обучение/сохранение/загрузка модели, временное разбиение и очистка CSV.

`--exact-small` разрешает полный перебор маршрутов до 8 заявок для проверки корректности. Он комбинаторно дорог и не предназначен для основных задач. `global_optimal=True` выставляется только для полной модели малой задачи при подтверждении всех последовательных этапов решателем. Статус `OPTIMAL_IN_POOL` на большой задаче не означает глобальный оптимум.

Обязательная базовая эвристика реализована отдельно: заявки строго во входном порядке, первый допустимый инженер, добавление только в конец маршрута. `--workforce-bound` считает нижнюю границу численности через релаксацию без поездок и порядка работ. Граница условна на зафиксированные количества обслуженных срочных и всех заявок; она не доказывает минимум расстояния.
