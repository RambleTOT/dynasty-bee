# Воспроизведение метрик алгоритма на кейсе Билайн Бизнес

Этот каталог проверяет **алгоритм из `../../dispatch/`** на исходных CSV кейса. Второй копии решателя здесь нет. Проверка автономна и не измеряет время ответа веб-приложения.

## Один запуск

Проверенное окружение: CPython 3.13.5 и версии библиотек из `requirements.txt`.

```bash
cd routing_algorithm/beeline_optimizer_v2_final/benchmark/case_2026
uv python install 3.13.5
uv venv --python 3.13.5 .venv
uv pip install --python .venv/bin/python -r requirements.txt
PYTHON_BIN=.venv/bin/python ./reproduce.sh
```

Команда заново строит подготовленные данные из шести CSV и синтетическую историю, сверяет их SHA-256 с `EXPECTED_INPUT_SHA256.json`; пересчитывает опубликованную сводку из сырых результатов; повторяет оценку контрольного распределения; обучает демонстрационную ML-модель; запускает тесты и все задачи benchmark. Итог — `REPRODUCTION OK`. Сгенерированные входы и подробности каждого этапа сохраняются в `reports/reproduced/` (эта папка не включена в Git).

Эталонная сводка из сохранённых результатов проверяется **точно**. Повторное обучение ML при тех же версиях на macOS arm64 также совпало точно; на другой архитектуре проверка допускает небольшое расхождение CatBoost (MAE ±1 мин, покрытие ±2 п. п., AUC ±0,02, Brier/ECE ±0,01). Строгая проверка обучения: `.venv/bin/python scripts/verify_reproduction.py --full --strict-ml` после запуска `reproduce.sh`.

Опубликованные значения пересчитываются из `reports/reference/*.json` в `EXPECTED_METRICS.json`. Эталон получен на коде этого репозитория в CPython 3.13.5 на macOS arm64. Сам решатель использует лимит времени: повторный прогон проверяется по покрытию каждого ранга, числу инженеров и ограничениям; километры, мягкий штраф и секунды могут немного меняться на другом CPU. Это не заявка на глобальный оптимум больших задач.

Для отдельно помеченной **синтетической ML-демонстрации**: 12 000 записей, хронологическое деление 8 400 / 1 800 / 1 800; MAE медианной длительности 10,96 мин, покрытие верхней оценки 90,94%; ROC-AUC первого устранения 0,732, опоздания 0,867, успешного визита 0,736. Переранжирование принято на 3/3 участках, среднее снижение **модельного** риска в эталонном прогоне 3,43%. Эти числа не оценивают качество на реальных выездах.

### Происхождение данных и допущения

- В `data/raw_case/beeline_case_csv/` — шесть таблиц кейса: заявки и контрольное распределение по трём участкам. Для читаемого diff они перекодированы из Windows-1251 в UTF-8 **без изменения ячеек**. Порядок заявок, типы, окна, район и адресные строки взяты из них.
- В CSV нет полного набора координат, дорожных матриц, смен, навыков и транспорта инженеров. `dispatch/beeline_benchmark_v3.py` **воспроизводимо моделирует** недостающие поля. Подготовленные данные создаются с seed 42 в `reports/reproduced/prepared/`; девять основных прогонов используют seed 1–3 на каждом участке.
- FIFO назначает заявку первому допустимому инженеру в исходном порядке и не оптимизирует план глобально. При сравнении пробега учитывайте, что FIFO выполняет существенно меньше заявок.
- Контрольное распределение содержит исторические назначения. Для его оценки принят порядок строк внутри каждой бригады; время в пути, длительность и характеристики инженеров взяты из той же модели. Показатели нарушений и пробега диспетчера — **оценка реконструкции**, а не измерение фактической работы.
- `reports/reproduced/synthetic_ml_history.csv` создаётся из `scripts/generate_synthetic_history.py` для демонстрации обучения и безопасного изменения плана. Его MAE, AUC и снижение модельного риска **не являются качеством на истории Билайна**. ML-проверка здесь отдельная от основного алгоритмического результата.

Основные файлы: `scripts/benchmark_submission.py` запускает задачи алгоритма, `scripts/rebuild_metrics.py` строит точную сводку, `scripts/verify_reproduction.py` проверяет её и инварианты повторного прогона. Исходные результаты хранятся в `reports/reference/`, поэтому пересчёт таблицы можно проверить независимо от нового запуска эвристики.
