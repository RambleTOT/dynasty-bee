# Интеллектуальный сервис планирования рабочих маршрутов для инженеров

**Команда Dynasty** · ЛЦТ 2026 · Кейс №3 «Билайн Бизнес»

Помощник диспетчера: распределяет заявки между инженерами, строит маршруты, показывает их на карте, перестраивает план при изменениях и простыми словами объясняет каждое решение.

## Схема решения

```
CSV (заявки, инженеры)
      ↓
  Адаптер данных — нормализация, маппинг типов заявок на навыки
      ↓
  Предрасчёт — геокодинг адресов + матрица расстояний и времени в пути
      ↓
  Алгоритм распределения — проверка трёх ограничений, порядок посещения
      ↓
  API (FastAPI)
      ↓
  Веб-интерфейс (React) — диспетчер, оператор, инженер:
  карта с маршрутами · план по инженерам · объяснения назначений ·
  неназначенные заявки с причинами · метрики и сравнение с базовым
  вариантом · перепланирование
```

- **Данные** — CSV в выданном формате Билайна: по каждому участку файл заявок и, по желанию, контрольное распределение диспетчера. Диспетчер загружает их в окне «Загрузка CSV», разбирает файлы бэкенд. Файлы кейса в репозиторий не входят.
- **Алгоритм** — распределение заявок и построение маршрута для каждого инженера с проверкой квалификации, времени и транспорта.
- **Интерфейс** — веб-приложение на три роли:
  - диспетчер (десктоп): календарь заявок, загрузка CSV, день на карте и таймлайне, сравнение с FIFO и реальным диспетчером, события и предложения, версии плана;
  - оператор (десктоп): поиск заявки, запись клиента в свободное окно, перенос и отмена, авария;
  - инженер (телефон): маршрут на день, статусы визитов, карта.

  Браузеру нужен интернет: карта, шрифт, подсказки адресов.

### Frontend (`frontend/`)

**Требования.** Node.js 20: в `frontend/.nvmrc` — `20`, в `package.json` — `"engines": { "node": ">=20" }`. Для `npm run check` нужна Node 20.19 или новее: линтер тянет пакет `eslint-visitor-keys` с требованием `^20.19.0 || ^22.13.0 || >=24` (`package-lock.json`). Пакеты ставит npm по `package-lock.json`.

```bash
cd frontend
nvm use        # версия из .nvmrc, если стоит nvm
npm ci         # зависимости строго по package-lock.json
npm run dev    # dev-сервер Vite: http://localhost:5173
```

- **Порт** 5173 задан в `frontend/vite.config.ts` (`server.port`). Если он занят, Vite возьмёт следующий свободный (`strictPort` не включён) и напишет адрес в консоли.
- **Бэкенд.** Dev-сервер проксирует `/api/*` (и WebSocket) на стенд `https://api.bee-dynasty.ru`, поэтому свой бэкенд поднимать не обязательно. Другой адрес задаётся переменной `DEV_API_TARGET` в командной строке, например `DEV_API_TARGET=http://127.0.0.1:8001 npm run dev`.
- **Вход** — по логину и паролю роли: диспетчер, оператор или инженер. Учётки заводит бэкенд, пароли в репозитории не хранятся.
- **Дальше:** войти диспетчером → «Загрузить CSV» → выбрать файлы участка → «Загрузить» → «Открыть день» → «Построить план». Как устроена загрузка — [docs/FRONTEND.md](docs/FRONTEND.md#загрузка-csv).

Остальные команды (`frontend/package.json`):

## Сценарий демонстрации

1. Войти диспетчером (`dispatcher`).
2. В календаре нажать «Загрузить CSV», выбрать файл заявок участка → «Загрузить» → «Открыть день». Контрольное распределение нужно, чтобы сравнить с реальным диспетчером. На сегодня бэкенд создаёт демо-день участка сам: его можно открыть из календаря без загрузки.
3. «Построить план» — план считается и сразу публикуется инженерам.
4. Посмотреть маршруты бригад на карте и таймлайне.
5. Открыть заявку на карте — карточка объясняет назначение по трём ограничениям: «Квалификация», «Время», «Ресурс».
6. «Добавить событие»: «Срочная заявка», «Отмена» или «Инженер недоступен». Сервис считает предложение и показывает, что изменится. Дальше — «Принять изменения», «Отклонить» или «Править вручную»; принятое предложение становится новой версией плана.
7. Панель «Сравнение планов» — наш план, базовый FIFO и реальный диспетчер по двум обязательным метрикам: «Задействовано инженеров» и «Пробег суммарно, км».
8. Другие роли:
   - оператор (`operator`) находит заявку, записывает клиента в свободное окно, переносит или отменяет;
   - инженер (`eng-east-01`, с телефона) видит маршрут на день и отмечает статусы визитов.

## Результаты

Сравнение по двум обязательным метрикам на данных кейса за 17.08.2026: наш алгоритм · базовый вариант FIFO · реальное распределение диспетчера из контрольной выгрузки.

| Участок | Инженеров: наш / FIFO / диспетчер | Пробег, км: наш / FIFO / диспетчер | Без исполнителя: наш / FIFO / диспетчер |
|---|---|---|---|
| Восток | **9** / 12 / 12 | **285,4** / 276,9 / 328,7 | **0** / 33 / 2 |
| Юго-восток | **11** / 12 / 12 | **363,5** / 456,5 / 401,3 | 3 / 40 / 0 |
| Югоцентр | **7** / 11 / 11 | **226,2** / 321,0 / 371,5 | **0** / 21 / 0 |

Итого по трём участкам: покрытие **98,2%** против 54,3% у FIFO, медиана **9** задействованных инженеров против 12, медианный пробег **285,4 км** против 321,0. Обязательные ограничения не нарушены ни разу; в историческом плане диспетчера нарушения есть в 166 визитах из 203. Медианное время расчёта плана — **1,74 с**.

Пробег по каждому инженеру отдельно отображается в интерфейсе на экране дня и в сравнении планов.

**Базовый вариант** задан по ТЗ: заявки обрабатываются по порядку поступления и назначаются первому по порядку во входных данных доступному инженеру, удовлетворяющему обязательным ограничениям; порядок посещения совпадает с порядком назначения; глобальная оптимизация не выполняется. Реализация — `dispatch/evaluate.py: baseline`, см. [docs/SOLUTION.md](docs/SOLUTION.md) §4.

> Сравнивать пробег корректно только при сопоставимом охвате: у FIFO треть заявок остаётся без исполнителя, поэтому его маршруты короче за счёт невыполненной работы.

## Известные ограничения прототипа

Каждое ограничение закрывается одним из этапов плана развития ниже.

- **Нет интеграции с BeeKeeper.** Заявки дня загружаются CSV-файлом, статусы визитов отмечает инженер в приложении, а срочные заявки, отмены и недоступность бригады диспетчер вводит событиями.
- **Длительность работ — норматив по типу заявки** ([docs/DATA.md](docs/DATA.md) §5): фактическая длительность не учитывается.
- **Оборудование на день не планируется:** в данных кейса его нет, в ТЗ это дополнительное усложнение. **Окно клиента фиксированное:** работа начинается только внутри окна.
- **Учётные записи инженеров — только на трёх участках кейса.** Новый участок подключается загрузкой файла, план для него строится, но его инженеры в приложение пока не входят.
- **Координаты адресов даёт внешний сервис** — Геокодер Яндекса, запасной — Nominatim (OpenStreetMap), с кэшем. Ненайденный адрес ставится в точку офиса участка и попадает в отчёт загрузки.
