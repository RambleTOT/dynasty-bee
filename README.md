# Интеллектуальный сервис планирования рабочих маршрутов для инженеров

Помощник диспетчера выездных инженеров оператора связи: распределяет заявки между инженерами, строит маршруты, показывает их на карте, перестраивает план при изменениях и простыми словами объясняет каждое решение.

## Схема решения

```
CSV или JSON (заявки, инженеры)
      ↓
  Адаптер данных — нормализация, маппинг типов заявок на навыки
      ↓
  Предрасчёт — геокодинг адресов + матрица расстояний и времени в пути
      ↓
  Алгоритм распределения — проверка трёх ограничений, порядок посещения
      ↓
  API (FastAPI)
      ↓
  Веб-интерфейс (React) — диспетчер, оператор, инженер:
  карта с маршрутами · план по инженерам · объяснения назначений ·
  неназначенные заявки с причинами · метрики и сравнение с базовым
  вариантом · перепланирование
```

- **Данные** — CSV в выданном формате оператора связи: по каждому участку файл заявок и, по желанию, контрольное распределение диспетчера. Диспетчер загружает их в окне «Загрузка CSV», разбирает файлы бэкенд. Шесть файлов для проверки алгоритма включены в [benchmark](routing_algorithm/beeline_optimizer_v2_final/benchmark/case_2026/). JSON (инженеры и заявки) загружается через API — `POST /api/v1/data/load` или `/data/load-files`, формат и пример — [docs/DATA.md](docs/DATA.md) §1.
- **Алгоритм** — распределение заявок и построение маршрута для каждого инженера с проверкой квалификации, времени и транспорта.
- **Интерфейс** — веб-приложение на три роли:
  - диспетчер (десктоп): календарь заявок, загрузка CSV, день на карте и таймлайне, сравнение с FIFO и реальным диспетчером, события и предложения, версии плана;
  - оператор (десктоп): поиск заявки, запись клиента в свободное окно, перенос и отмена, авария;
  - инженер (телефон): маршрут на день, статусы визитов, карта.

  Браузеру нужен интернет: карта, шрифт, подсказки адресов.

## Запуск

### Backend (`backend/`)

**Требования.** Python 3.11+ (проверено на 3.12), зависимости — `backend/requirements.txt`.

```bash
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env          # значения по умолчанию — SQLite
uvicorn app.main:app --reload --port 8000
```

- **API** — http://localhost:8000, Swagger — http://localhost:8000/docs.
- **База** — SQLite по умолчанию; PostgreSQL задаётся `DATABASE_URL`.
- **Демо-учётки** создаются при старте, пароль — значение `DEMO_PASSWORD` из `.env`
  (в `.env.example` — `change-me-on-stand`): диспетчер `dispatcher`, оператор `operator`,
  инженеры `eng-east-01…12`, `eng-se-01…12`, `eng-sc-01…11`.
- **Данные** — CSV загружаются бэкендом, разбор файлов и маппинг типов заявок на
  навыки описаны в [docs/DATA.md](docs/DATA.md); логика оптимизации и ограничения —
  в [docs/SOLUTION.md](docs/SOLUTION.md).
- **Алгоритм** — оптимизатор в `routing_algorithm/`,
  подключается адаптером `backend/app/services/algorithm_adapter.py`.

**Docker (PostgreSQL).** Из корня репозитория:

```bash
cp .env.example .env
docker compose up -d --build api        # API на http://localhost:8000
```

Локальный OSRM (автомобильные маршруты) — необязательный профиль: `bash osrm/init_osrm.sh`
и `docker compose --profile osrm up -d osrm`. Без него машина считается через
OpenRouteService (если задан `ORS_API_KEY`), иначе по прямой.

**Тесты.**

```bash
cd backend
pip install -r requirements-dev.txt
python -m pytest
```

Подробнее — [backend/README.md](backend/README.md).

### Frontend (`frontend/`)

**Требования.** Node.js 20.19 или новее (`frontend/.nvmrc`, `engines` в `package.json`), npm 10+. Пакеты ставит npm по `package-lock.json`.

```bash
cd frontend
nvm use        # версия из .nvmrc, если стоит nvm
npm ci         # зависимости строго по package-lock.json
npm run dev    # dev-сервер Vite: http://localhost:5173
```

- **Порт** 5173 задан в `frontend/vite.config.ts` (`server.port`). Если он занят, Vite возьмёт следующий свободный (`strictPort` не включён) и напишет адрес в консоли.
- **Бэкенд.** Dev-сервер проксирует `/api/*` (и WebSocket) на стенд `https://api.bee-dynasty.ru`, поэтому свой бэкенд поднимать не обязательно. Другой адрес задаётся переменной `DEV_API_TARGET` — в командной строке или в `frontend/.env.local`, например `DEV_API_TARGET=http://127.0.0.1:8000 npm run dev`.
- **Вход** — по логину и паролю роли: диспетчер, оператор или инженер. Учётки заводит бэкенд, пароли в репозитории не хранятся.
- **Дальше:** войти диспетчером → «Загрузить CSV» → выбрать файлы участка → «Загрузить» → «Открыть день» → «Построить план». Как устроена загрузка — [docs/FRONTEND.md](docs/FRONTEND.md#загрузка-csv).

Остальные команды (`frontend/package.json`):

| Команда | Что делает |
|---|---|
| `npm run build` | проверка типов и прод-сборка в `frontend/dist/` |
| `npm run preview` | раздать собранный `dist/` на http://localhost:4173, `/api` — через тот же прокси |
| `npm run check` | `tsc --noEmit` для приложения и `vite.config.ts`, затем `eslint .` |
| `npm test` | тесты (vitest, jsdom) |

| `npm run design:unpack` | распаковать макеты из `frontend/design/` (папка в репозиторий не входит) |
| `npm run deploy` | выкладка на сервер команды (`scripts/deploy.sh`, нужен SSH-ключ) |

**Переменные окружения.** Шаблон — `frontend/.env.example`, свои значения — в `frontend/.env.local` (в git не попадает). Переменные `VITE_*` Vite читает при запуске и сборке.

## Сценарий демонстрации

1. Войти диспетчером (`dispatcher`).
2. В календаре нажать «Загрузить CSV», выбрать файл заявок участка → «Загрузить» → «Открыть день». Контрольное распределение нужно, чтобы сравнить с реальным диспетчером. На сегодня бэкенд создаёт демо-день участка сам: его можно открыть из календаря без загрузки.
3. «Построить план» — план считается и сразу публикуется инженерам.
4. Посмотреть маршруты бригад на карте и таймлайне.
5. Открыть заявку на карте — карточка объясняет назначение по трём ограничениям: «Квалификация», «Время», «Ресурс».
6. «Добавить событие»: «Срочная заявка», «Отмена» или «Инженер недоступен». Сервис считает предложение и показывает, что изменится. Дальше — «Принять изменения», «Отклонить» или «Править вручную»; принятое предложение становится новой версией плана.
7. Панель «Сравнение планов» — наш план, базовый FIFO и реальный диспетчер по двум обязательным метрикам: «Задействовано инженеров» и «Пробег суммарно, км».
8. Другие роли:
   - оператор (`operator`) находит заявку, записывает клиента в свободное окно, переносит или отменяет;
   - инженер (`eng-east-01`, с телефона) видит маршрут на день и отмечает статусы визитов.

## Пример объяснения диспетчеру

Карточка заявки на экране дня: нажать на заявку на карте или в таймлайне, затем «Подробнее». Участок Восток, заявки из выданного CSV, план построен сервисом. Текст — как на экране, адрес опущен.

```text
№76678 · Локальная заявка · Работа с кабелем · Запланирована
Временное окно: 10:00–12:00
Приезд · начало · окончание: 10:10 · 10:10 · 10:40
Длительность: 30 мин по нормативу
Требуемый транспорт: Автомобиль
Инженер: Бригада Комарь · автомобиль
№ в маршруте · от предыдущей: 1 из 10 · 4,5 км

Почему этот инженер
Бригада Комарь: есть навык «Локальные работы», начнёт в 10:10 в окне 10–12,
едет на автомобиле, 4,5 км от старта.

Подробнее
Квалификация — Нужен навык «Локальные работы», у бригады есть
Время — Приезд 10:10, начало 10:10 (окно 10–12), окончание 10:40, смена до 22:00, запас 110 мин
Ресурс — Нужен автомобиль (работа с кабелем), бригада на автомобиле

Инженер владеет требуемым навыком «Локальные работы».
Доступен требуемый транспорт — Автомобиль.
Начало работ 10:10 попадает во временное окно 10:00–12:00.
Маршрут завершается в 10:40, до конца смены 22:00.
Заявка стоит 1-й в маршруте; суммарный пробег маршрута 28.5 км.

Почему не другие
Бригада Соколов — нет навыка
Бригада Мельников — нет навыка
Бригада Матвеев — нет навыка
```

Строку «Почему этот инженер», три ограничения и «Почему не другие» собирает фронтенд из фактов плана (`frontend/src/adapters/constraints.ts`). Пять строк после ограничений — объяснение бэкенда из ответа `GET /api/v1/planning/{id}`, поле `explanations[].reasons` (`backend/app/services/explanation_service.py`).

## Результаты

Сравнение по двум обязательным метрикам на данных кейса за 17.08.2026. Наш алгоритм и FIFO — медианы трёх сценариев на каждом участке; диспетчер — реконструкция контрольной выгрузки с моделируемыми временем пути и характеристиками инженеров. [Методика и воспроизведение](routing_algorithm/beeline_optimizer_v2_final/benchmark/case_2026/README.md).

| Участок | Инженеров: наш / FIFO / диспетчер | Пробег, км: наш / FIFO / диспетчер | Без исполнителя: наш / FIFO / диспетчер |
|---|---|---|---|
| Восток | **9** / 12 / 12 | **285,4** / 276,9 / 328,7 | **0** / 33 / 2 |
| Юго-восток | **11** / 12 / 12 | **364,1** / 456,5 / 401,3 | 3 / 40 / 0 |
| Югоцентр | **7** / 11 / 11 | **226,2** / 321,0 / 371,5 | **0** / 21 / 0 |

По девяти прогонам (205 исходных заявок × 3 сценария): покрытие **604/615 = 98,2%** против **334/615 = 54,3%** у FIFO, медиана **9** задействованных инженеров против 12, медианный пробег **285,4 км** против 321,0. В планах алгоритма нет нарушений жёстких ограничений. При реконструкции контрольного распределения модель отмечает нарушения в 166 визитах из 203 назначенных.

Пробег по каждому инженеру отдельно отображается в интерфейсе на экране дня и в сравнении планов.

**Базовый вариант** задан по ТЗ: заявки обрабатываются по порядку поступления и назначаются первому по порядку во входных данных доступному инженеру, удовлетворяющему обязательным ограничениям; порядок посещения совпадает с порядком назначения; глобальная оптимизация не выполняется. Реализация — `dispatch/evaluate.py: baseline`, см. [docs/SOLUTION.md](docs/SOLUTION.md) §4.

> Пробег алгоритма и FIFO не показывает экономию на одинаковом объёме работ: FIFO оставляет без исполнителя 281 из 615 заявок в девяти сценариях.

## Известные ограничения прототипа

Закрываются этапами плана развития (раздел ниже):

- **Нет интеграции с BeeKeeper.** Заявки дня загружаются CSV-файлом, статусы визитов отмечает инженер в приложении, а срочные заявки, отмены и недоступность бригады диспетчер вводит событиями.
- **Длительность работ — норматив по типу заявки** ([docs/DATA.md](docs/DATA.md) §5): фактическая длительность не учитывается.
- **Оборудование на день не планируется:** в данных кейса его нет, в ТЗ это дополнительное усложнение. **Окно клиента фиксированное:** работа начинается только внутри окна.
- **Учётные записи инженеров — только на трёх участках кейса.** Новый участок подключается загрузкой файла, план для него строится, но его инженеры в приложение пока не входят.
- **Координаты адресов даёт внешний сервис** — Геокодер Яндекса, запасной — Nominatim (OpenStreetMap), с кэшем. Ненайденный адрес ставится в точку офиса участка и попадает в отчёт загрузки.

Упрощено для MVP, в план не входит:

- **Пробки не учитываются.** Машина едет по дорогам OpenStreetMap (свой OSRM); пешком, на велосипеде и на общественном транспорте расстояние считается по прямой ×1,3, время — по средней скорости, у общественного транспорта — с ожиданием ([docs/SOLUTION.md](docs/SOLUTION.md) §6).
- **Обед и перерывы в смене не моделируются.**
- **Возврат на базу после последней заявки не считается** — по ТЗ для MVP он не нужен.
